# CWE Visualizer — Design

## Purpose

A learning/practice project: a visual explorer for the full CWE (Common
Weakness Enumeration) corpus published by MITRE, deployed on Vercel's free
plan. The point of the exercise is as much the GitHub-driven build/deploy
pipeline (issue → PR → review → merge, plus a fully automated daily
data-freshness check) as the visualizer itself, so the frontend is kept
deliberately simple and the pipeline gets the design attention.

## Scope

**In scope:**
- Visualize the full CWE corpus (every `Weakness` entry MITRE publishes) as
  one graph, not a single curated MITRE "view."
- A tree-first UI: `ChildOf`/`ParentOf` edges drive a collapsible hierarchy;
  all other relationship types (`PeerOf`, `CanFollow`, `CanPrecede`,
  `CanAlsoBe`, `Requires`, `StartsWith`, etc.) surface in a detail panel when
  a node is selected, plus a search box to jump directly to any CWE.
- Data is fetched and parsed once, ahead of time (locally in dev, or during
  the Vercel build) — the running app never fetches from MITRE or reparses
  XML itself; it only reads a prebuilt static JSON file.
- A daily GitHub Actions job that detects when MITRE's published data has
  changed and triggers a redeploy — with no data committed to the repo, and
  no state committed either.
- Every human/agent-authored change goes through an issue → branch → PR →
  CI → manual review → merge flow, enforced by branch protection on `main`.
- A pre-commit hook (eslint + full test suite) via Husky + lint-staged.

**Explicitly out of scope for this iteration:**
- CWE **Categories** and **Views** (MITRE constructs above individual
  Weakness entries) — only `Weakness` entries and their
  `Related_Weaknesses` edges are parsed and shown. **Follow-up:** file a
  GitHub issue after the initial version ships to add these.
- An automated LLM-based PR reviewer. Review is manual for now (the
  repo owner, optionally invoking an agent like Claude Code by hand).
- Any account system, multi-view switching, or server-side
  rendering/API routes — the app is a fully static SPA.

```
│   │   └── DetailPanel.tsx      # selected node's info + non-hierarchy relations
│   └── lib/
│       └── graph.ts             # client-side indices: childrenOf, relatedTo, search
├── public/data/                 # gitignored — generated by prepare-data.ts
│   ├── cwe.json

├── test/fixtures/               # small hand-crafted XML+zip fixtures, no real network
├── .github/workflows/
│   ├── ci.yml                   # lint + test + build, on every PR
│   └── update-data.yml          # daily: compare MITRE vs deployed meta.json; maybe deploy

```

No `data/` directory separate from `public/data/`: since the app fetches
the JSON at runtime rather than importing it at build time, one location
serves dev, build, and the fast-path cache check identically.

## Data pipeline (`scripts/prepare-data.ts`)

**Source.** MITRE publishes the full CWE corpus as a single XML file inside
a zip archive (`cwec_latest.xml.zip`). The XML root (`Weakness_Catalog`)
carries a `Version` and `Date`; each `Weakness` entry has an ID, name,
abstraction level, status, a plain-text description (verified against the
live catalog: `Weakness/Description` never contains inline markup, so no
flattening step is needed — that markup does appear elsewhere, e.g.
`Mitigation` descriptions, just not in the field this app reads), and
`Related_Weaknesses` — each naming a `Nature` (`ChildOf`, `ParentOf`,
`PeerOf`, `CanFollow`, `CanPrecede`, `CanAlsoBe`, `Requires`, `StartsWith`)
and a target CWE ID.

**Libraries:** `fast-xml-parser` (pure JS, no native deps) for XML, and
`adm-zip` for the archive — a hand-rolled zip reader was considered (Node's
built-in `node:zlib` only provides the raw inflate algorithm, not zip
container parsing) but rejected: owning a narrow, hand-written parser for a
binary container format is exactly the kind of fragile code not worth
carrying for one build script. `adm-zip` is a maintained dependency instead.

**Fast path.** Every invocation first does a lightweight check before
touching the network for real data:
1. `HEAD` the MITRE zip URL → read its `Last-Modified` header.
2. Compare against the value recorded in the *currently relevant* source of
   truth (see "No committed state" below).
3. If they match, exit immediately — no download, no parse, no output
   changes.

(MITRE's zip download does not send an `ETag` header — verified directly
against the live endpoint — so `Last-Modified` is the freshness signal
instead; it's present, standard, and just as suitable for an equality
check.)

**Slow path** (`Last-Modified` differs, or no prior state exists): download
the zip, extract the single XML entry, parse it, and write:

```json
// public/data/cwe.json
{
  "meta": { "cweVersion": "4.15", "lastModified": "Thu, 30 Apr 2026 09:15:04 GMT", "generatedAt": "2026-08-23T00:00:00Z" },
  "nodes": {
    "79": {
      "id": "79", "name": "Cross-site Scripting", "abstraction": "Base",
      "status": "Stable", "description": "...",
      "url": "https://cwe.mitre.org/data/definitions/79.html"
    }
  },
  "edges": [ { "from": "79", "to": "80", "type": "ChildOf" } ]
}
```

`public/data/meta.json` duplicates the `meta` block alone, as a small,
cheap-to-fetch file for the daily check (see below) to read without pulling
down the whole graph.

Nodes and edges are shipped flat/normalized — no pre-baked tree — the
client builds parent/child indices once on load, which is trivial at
roughly 1,000-1,500 entries. Tree roots are any node with no outgoing
`ChildOf` edge, including fully isolated entries; nothing from the corpus
is dropped.

**No committed state.** Neither `public/data/*.json` nor any version marker
is ever committed to git (all gitignored). Locally, the fast path's "prior
state" is whatever `public/data/meta.json` already sits on disk from a
previous local run (if any). In CI/Vercel, each build is a fresh checkout
with no such file, so the slow path always runs there — which is fine,
since Vercel only ever rebuilds when the daily workflow has already
confirmed real upstream change (see below).

**Error handling.**
- `Last-Modified` check fails to reach MITRE: if a local `meta.json` cache exists
  (dev only), warn and reuse the stale cache rather than blocking; if not
  (first run, or a cache-less CI/Vercel build), fail loudly.
- The real download fails, zip extraction breaks, or the XML is missing
  its expected root/version: hard-fail with a clear error message. A build
  producing bad or partial data is worse than a build that doesn't happen.
- No streaming — the source file is a few MB; loading fully into memory is
  fine at this scale.

## Frontend (Vite + React SPA)

- **`graph.ts`**: fetches `public/data/cwe.json` once on load and builds
  two in-memory indices — `childrenOf: Map<id, id[]>` (from `ChildOf`
  edges) and `relatedTo: Map<id, Edge[]>` (every other relationship type)
  — plus a flat array for search.
- **`Tree.tsx`**: renders roots with expand/collapse; children are only
  mounted once their parent is expanded (avoids rendering ~1,500 nodes up
  front). The selected node's ID lives in a URL query param, so a node is
  linkable and survives a refresh.
- **`SearchBox.tsx`**: client-side substring match over `id` + `name`
  across the full node list — no search index library needed at this
  scale. Picking a result sets the selection, which the tree reacts to by
  auto-expanding ancestors down to that node and scrolling it into view.
- **`DetailPanel.tsx`**: shows the selected node's description,
  abstraction/status, and its non-`ChildOf` relationships as a labeled,
  clickable list (clicking jumps selection to that CWE).
- **Error state**: if `cwe.json` fails to load at runtime (shouldn't happen
  given it's a static build artifact, but covers a bad deploy), show a
  plain error message rather than a blank screen.

## Testing (Vitest)

- **`prepare-data.ts`** (run directly by Node 24's native TypeScript
  support — see Architecture): unit tests against a small hand-crafted
  fixture XML+zip under `test/fixtures/` covering multiple relationship
  types — never touches the real network. Covers parsing shape, root
  detection, and the fast-path `Last-Modified`-compare logic (HTTP mocked).
  (Description text needs no markup-flattening — verified against the real
  MITRE catalog that `Weakness/Description` is always plain text.)
- **`graph.ts`**: unit tests for index-building and search logic against a
  small fixture graph object — no XML involved.
- **Components**: React Testing Library tests for expand/collapse,
  search-to-select, and detail panel content, driven by a fixture
  `cwe.json`.
- **CI (`ci.yml`)**: lint + `vitest run` + `npm run build` on every PR. The
  build step runs `prepare-data.ts` for real (hits MITRE) to prove the
  build doesn't break — an accepted, minor real-network dependency in CI
  given PRs are infrequent.

## Deployment

**`package.json` scripts:**
```json
{
  "scripts": {
    "prepare-data": "node scripts/prepare-data.ts",
    "predev": "npm run prepare-data",
    "dev": "vite",
    "prebuild": "npm run prepare-data",
    "build": "vite build",
    "preview": "vite preview",
    "lint": "eslint .",
    "test": "vitest run",
    "prepare": "husky"
  }
}
```

**Vercel:** no `vercel.json` required — Vite is a zero-config-detected
framework on Vercel, and `npm run build` already runs `prebuild` via
standard npm lifecycle, so data prep happens as part of the build Vercel
already does. One manual one-time setup: create a Vercel Deploy Hook and
store its URL as a GitHub Actions secret (`VERCEL_DEPLOY_HOOK_URL`).

**Local run:** `npm install && npm run dev` — `predev` prepares the data
(fast-pathing on repeat runs), then Vite serves the SPA.

## GitHub Actions

**`ci.yml`** — on every PR: install, lint, `vitest run`, `npm run build`.

**`update-data.yml`** — on a daily schedule:
1. `HEAD` MITRE's CWE zip → current `Last-Modified` header.
2. `GET https://<deployed-domain>/data/meta.json` → the `Last-Modified`
   value the live site was last built from.
3. If they differ, POST to the Vercel deploy hook. Vercel's build runs
   `prepare-data.ts` fresh (ephemeral, no cache → always takes the slow
   path), regenerating `cwe.json`/`meta.json` with the current data and
   deploying it.
4. If they match, do nothing.

This workflow never commits or pushes anything — its only side effect,
when data has changed, is one HTTP POST to a deploy hook. It therefore
needs no exception to branch protection or the issue/PR requirement:
there is nothing for it to bypass.

## Contribution workflow

- Every change starts as a GitHub issue (what/why).
- A branch + PR references the issue (`Closes #N`).
- `ci.yml` must pass before merge.
- Review is manual — the repo owner, optionally invoking an agent (e.g.
  Claude Code via `/code-review`) by hand. No automated reviewer bot in
  this iteration.
- Branch protection on `main` requires a PR with passing status checks.
  Since `update-data.yml` never pushes, this rule applies uniformly with
  no carve-outs.
- One lightweight issue template to start (what/why); more structured
  templates can be added later if that turns out to be useful.
